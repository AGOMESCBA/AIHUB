O que é o Middleware de Proteção SQL
O Middleware SQL é a camada de segurança obrigatória que fica entre a IA e o banco de dados do seu ERP. Toda vez que um usuário faz uma pergunta em linguagem natural, a IA gera um comando SQL para buscar a resposta. Antes desse SQL chegar ao banco, o middleware o intercepta, analisa e decide: aprovar, modificar ou bloquear.
Pense no middleware como um porteiro: a IA pode ser criativa, mas só entra no banco o que for seguro, limitado e dentro das regras que você configurou aqui.
Posição no pipeline do IA Command
O middleware age neste ponto do fluxo de resposta:
1. Usuário envia mensagem no WhatsApp
2. IA interpreta a intenção e o período
3. IA gera o SQL para responder
4. Middleware analisa o SQL ← você está aqui
5. SQL aprovado é executado no banco do ERP
6. Resultado é formatado e enviado de volta
Se o middleware bloquear o SQL, o usuário recebe uma mensagem de erro amigável e nenhuma consulta é feita ao banco.

O que o middleware NÃO faz
O middleware não executa o SQL — ele apenas valida e transforma. A execução no banco de dados é feita pelo módulo de conexão separado, que usa as credenciais configuradas na tela de Conexões. O middleware também não altera a lógica de negócio da query, não reescreve JOINs e não conhece o schema das tabelas — ele age em nível de texto.
Modelo de dados do Protheus
TRADICIONAL
Configuração padrão da maioria das instalações Protheus. Cada empresa tem suas próprias tabelas físicas no banco, identificadas por um sufixo numérico. Exemplo: a empresa "01" tem as tabelas SF1010, SD1010, SA2010. O isolamento entre empresas é garantido pelo próprio sufixo — não é necessário nenhum filtro adicional no SQL. Deixe os campos de Tenant, Campo empresa e Campo filial em branco.
LOBO_GUARA (Multi-empresa)
Modelo avançado onde múltiplas empresas compartilham as mesmas tabelas físicas. As tabelas não têm sufixo por empresa — em vez disso, cada registro tem um campo que identifica a qual empresa pertence. O middleware injeta automaticamente um filtro WHERE [campo_empresa] = '[tenant_id]' em todos os SQLs gerados pela IA, garantindo que uma empresa nunca enxergue dados de outra. Use apenas se o seu Protheus foi configurado neste modelo (consulte o DBA ou o parceiro TOTVS).
Campos do modelo LOBO_GUARA
Tenant ID — Código da empresa no ERP
É o código que identifica a sua empresa no banco de dados compartilhado. Pode ser numérico (01, 02) ou alfanumérico (T1, MATRIZ), dependendo de como o Protheus foi configurado. Este valor será inserido literalmente no filtro SQL gerado. Campo obrigatório quando o modelo for LOBO_GUARA.
Campo empresa na tabela
Nome do campo, dentro das tabelas do banco, que armazena o código da empresa. No modelo LOBO_GUARA de ERPs genéricos, este campo pode ser algo como EMP_ID ou COD_EMPRESA. No Protheus especificamente, o conceito equivalente é o campo [PREFIXO]_FILIAL, mas como cada tabela tem um prefixo diferente, este campo estático tem uso limitado — veja a aba Protheus para orientação específica.
Campo filial (opcional)
Usado quando o ERP separa o isolamento em dois níveis: empresa e filial. Preencha apenas se o seu ERP tiver um campo de filial distinto do campo de empresa. No Protheus, o campo _FILIAL já combina empresa e filial no mesmo valor — este campo raramente é necessário para instalações Protheus padrão.
Limites de execução
Limite de registros (SET ROWCOUNT)
Define o número máximo de linhas que qualquer consulta pode retornar. O middleware garante que o SQL sempre tenha um SET ROWCOUNT N antes do SELECT. Se a IA gerar um ROWCOUNT maior do que este limite, o middleware o rebaixa automaticamente para o valor configurado. Valor padrão: 10.000. Mínimo: 100. Máximo: 50.000. Consultas muito grandes impactam a performance do banco e o tempo de resposta no WhatsApp — mantenha em um valor razoável para o volume do seu ERP.
Timeout da consulta (ms)
Tempo máximo, em milissegundos, que uma consulta pode ficar rodando no banco antes de ser cancelada automaticamente. Evita que uma query mal gerada pela IA trave conexões ou consuma recursos do servidor por tempo indeterminado. Valor padrão: 30.000 ms (30 s). Mínimo: 5.000 ms. Máximo: 300.000 ms (5 min). Para relatórios analíticos complexos com JOINs em tabelas grandes, considere aumentar para 60.000–120.000 ms.
Tabelas bloqueadas
Lista de prefixos de tabelas que o middleware deve proibir completamente. Se o SQL gerado pela IA referenciar qualquer tabela cujo nome começa com um dos prefixos listados, a consulta é rejeitada antes de chegar ao banco e o usuário recebe uma mensagem de erro. O bloqueio é por prefixo — adicionar SE2 bloqueia SE2010, SE2990 e qualquer variação com sufixo.
Use para proteger tabelas de módulos que o usuário não deve acessar via WhatsApp, como financeiro (SE1, SE2), folha de pagamento (SRH), configurações do sistema (SY0–SY6) e usuários (SYP).
Campos sensíveis (alerta)
Lista de nomes de campos que devem gerar um alerta de auditoria quando referenciados pela IA. Ao contrário das tabelas bloqueadas, este mecanismo não bloqueia a consulta — ele apenas registra no log que um campo sensível foi acessado. Útil para rastrear consultas a dados como CNPJ de fornecedores, CPF de funcionários ou valores de custo.
Campos sensíveis geram alertas mas não protegem os dados. Se um campo não deve ser acessado em hipótese alguma, bloqueie a tabela inteira em vez de confiar apenas no alerta de campo.
Como o Protheus isola dados por empresa
No Protheus, o isolamento entre empresas é feito de duas formas dependendo da versão e configuração:
ModeloComo funcionaExemplo de tabela
TRADICIONAL
Mais comum		 Cada empresa tem tabelas físicas próprias com sufixo de 3 dígitos. O sufixo codifica empresa + filial. SF1010 = tabela SF1, empresa 01, filial 01
LOBO_GUARA
Menos comum		 Todas as empresas compartilham as mesmas tabelas físicas. O campo [PREFIXO]_FILIAL identifica empresa+filial em cada registro. SF1 compartilhada — filtro: F1_FILIAL = '0101'
Por que Campo empresa e Campo filial ficam em branco no Protheus
No Protheus, o campo de filial tem um prefixo diferente para cada tabela: F1_FILIAL (SF1), D1_FILIAL (SD1), C7_FILIAL (SC7), A2_FILIAL (SA2) e assim por diante. O middleware usa um único valor estático de campo — ele não consegue derivar automaticamente o prefixo correto para cada tabela no JOIN. Forçar um campo genérico como FILIAL quebraria o SQL gerado.
No IA Command, o filtro de filial do Protheus é resolvido diretamente no prompt da IA, que conhece o prefixo de cada tabela e o modo de compartilhamento (SX2). Configure a filial e o modo SX2 na tela de Conexões Protheus — não aqui.

Use o testador antes de salvar
A tela tem uma área de teste ao final da página. Cole um SQL real — de uma conversa no Monitor, por exemplo — e clique em Executar teste para ver exatamente o que o middleware fará: se vai aprovar, bloquear, quais alertas gerará e qual será o SQL final enviado ao banco. O teste não executa no ERP, é 100% seguro para qualquer SQL.
Sempre teste após alterar tabelas bloqueadas ou campos sensíveis. Uma configuração muito restritiva pode bloquear consultas legítimas e frustrar o usuário no WhatsApp.
Calibre os limites com base no seu ambiente
Limite de registros
Comece com 10.000 (padrão). Se usuários relatarem que respostas estão sendo cortadas em consultas analíticas, aumente para 20.000 ou 30.000. Valores muito altos aumentam o tempo de resposta e o consumo de memória no servidor de banco.
Timeout
30 segundos atende a maioria dos casos. Para consultas de BI com múltiplos JOINs em tabelas volumosas de NF, considere 60–90 segundos. Nunca coloque acima de 5 minutos — prefira otimizar o schema ou adicionar índices no banco do ERP.
Bloqueie com cuidado
Não bloqueie tabelas que o módulo configurado realmente precisa. Por exemplo, se o módulo de Compras usa SA2 (fornecedores), bloqueá-la vai quebrar todas as consultas que envolvem nome de fornecedor. Bloqueie apenas módulos completamente fora do escopo pretendido, como financeiro, folha de pagamento e configurações do sistema.
Um bloqueio excessivo não aparece como erro de configuração — ele se manifesta como "consulta não entendida" para o usuário no WhatsApp. Use o testador regularmente para verificar se as regras ainda fazem sentido.

Monitoramento contínuo
Acompanhe o Monitor do IA Command periodicamente para ver quais SQLs estão sendo gerados, se há bloqueios frequentes e se os alertas de campos sensíveis estão disparando. Um bloqueio recorrente pode indicar que a IA está tentando acessar uma tabela legítima bloqueada por engano — ou que um usuário está consultando dados fora do escopo autorizado.
